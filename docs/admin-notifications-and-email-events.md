# Admin inbox and automatic email events

The admin header bell and `/admin/notifications` share one authenticated feed. It combines supplier and seller applications, contact messages, support tickets/replies, supplier document uploads/replies, Deal Room messages, partnership bookings, website feedback, developer applications, payment-review requests and email-delivery alerts. Sources are queried in parallel, with up to 300 records per collection. The UI shows source failures rather than claiming an empty inbox. This is recent operational activity, not an unlimited historical archive.

Opening a notification adds its ID to the destination URL and displays the context banner. Seller/ticket screens select the record; generic supplier/contact lists filter to it; developer requests select the account/invoice; bookings and feedback choose the relevant Operations tab. Marking **Task done** changes only the notification task. It never approves payments, applications or documents. **Done** retains completed tasks and supports reopening. A later customer reply or submitted payment creates a new actionable item. Task read/completion state is stored under `users/{adminUid}/adminNotificationTasks`; archived task summaries retain only the category, reference and destination. Both API methods require the existing admin role and MFA session. No new public Firebase collection or direct client notification write is introduced.

`activityEmail` sends transactional confirmations through the branded encrypted mail queue. It adds stable event/record/revision idempotency keys and never emails API secrets, passwords, verification credentials or uploaded documents. On Vercel, activity delivery attempts use `waitUntil` after durable enqueueing. Existing retries, queue monitoring and admin alerts remain in place. Email failures do not undo completed domain operations. Draft autosave receipts are grouped hourly; repeated changes to the same key/profile within a minute share a receipt key to prevent floods. Marketing consent and newsletter delivery remain separate.

New confirmations cover supplier draft save/delete, requested document upload, supplier replies, contact messages, developer application/credit request/payment submission/cancellation, API-key creation/revocation/permission changes, spending/webhook settings, product/catalog saves/deletes, seller profile/commercial/notification settings, support creation/replies/closure/rating and successful password resets. Existing submission/review emails, booking emails, AIO action receipts, transcript delivery, admin replies, approvals, document requests and low-balance emails continue using their existing triggers.

Password recovery emails now use only Auronix delivery with `/reset-password?code=…` links. The credential is still validated/consumed by the existing authentication backend. The website completes the reset through its own endpoint and sends the security confirmation to the email returned by that trusted backend, never a caller-supplied address. The provider-hosted fallback email has been removed. Existing `oobCode` links continue to work. Reset credentials and passwords are not logged, reset pages use no-referrer/no-store, and Cloudflare checks are present on request and completion forms when configured.

Validation: `node --test tests/unit/*.cjs`, `npm run typecheck`, `npm run build`. Tests cover authorization, cross-admin task isolation, completion/reopening, new replies after completion, preserved source decisions, branded queue delivery, deduplication, consumed reset credentials and forged confirmation recipients. Browser review uses local fixtures for the admin bell, redirected task banner, Done workflow, themes and 320px layout. Live inbox acceptance and authenticated production operations require the deployed service configuration; no real password or financial transaction is exercised in QA.
